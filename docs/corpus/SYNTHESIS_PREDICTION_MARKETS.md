## 3. Honest Gap Analysis — Today → Live Money

**What exists**: data plant (52.77M trades), UUID mint + routing proof, signal research (19 Kalshi studies), a dry-run Kalshi order scaffold, and (in the platform gists) a paper-trading loop that never hit its 60-resolved/55% gate.

**What is missing**:

1. **Auth/keys**: no `KALSHI_KEY_ID`/`KALSHI_PRIVATE_KEY` (RSA-PSS signed REST); no Polygon wallet, USDC, or Polymarket API creds (key/secret/passphrase + allowances). Zero real orders have ever been placed by any SoMaCo system.
2. **Order lifecycle**: `kalshi_uuid_bot.py` covers create only — no cancel/amend, no fill polling (`GetFills`), no partial-fill handling, no WebSocket order/fill stream, no idempotent retry (the AustinSays outbox/saga patterns exist on paper only).
3. **Risk limits**: disposition/Kelly/correlation-guard logic lives in the Vercel gist code, not in this repo. No max-position, max-daily-loss, kill switch, or per-domain exposure caps in the execution path.
4. **Position tracking & P&L**: nothing. `uuid_trades` is other people's historical trades. There is no positions table, no fills table, no mark-to-market, no settlement reconciliation.
5. **Latency reality check — "HFT" is not realistic.** Kalshi is REST + WebSocket over the public internet, rate-limited (basic tier ~10–20 req/s), no colocation, no exchange-side latency guarantees; you're trading from a Windows desktop (OMEN-01). Round-trip order latency will be 50–300ms+; genuine HFT (µs, queue-position games) is off the table and the venue's tick size (1¢) and fee structure make it pointless anyway. Polymarket's CLOB is off-chain matching with on-chain settlement — same story. **The realistic latency class is "fast event-driven" (100ms–seconds), and the 1.5M ops/s bitmask filter is genuinely useful there**: pre-filtering thousands of streamed quote UUIDs in-process before strategy code runs. The right strategy families, in order of evidence strength:
   - **Maker/passive liquidity capture** — the repo's own `maker_vs_taker_returns` line of studies proves a persistent maker premium and NO-side bias on Kalshi; quote both sides inside the spread on liquid markets, sized small.
   - **Calibration edge** — `win_rate_by_price` + `mispricing_by_price` + Metaculus/Manifold cross-references (0x3AB–0x3AE) identify systematically mispriced buckets (longshot bias); slow, capacity-limited, but statistically grounded.
   - **Cross-venue arb Polymarket↔Kalshi** — same-event contracts diverge; the twin-pair divergence view (`v_twin_signal_pairs`, gist `e98cb194`) is exactly this pattern. Latency-tolerant (divergences persist minutes), but watch fees, Kalshi's ~$0.07×p×(1−p) fee curve, and event-definition mismatch risk.
   - **Event-driven news reaction** — the BTC-5-min Chainlink-lag trade from gist `12bbc1c3` is the template; seconds-scale, not HFT.
6. **The paper-trading gate was the right idea and was abandoned.** Reinstate it: no live capital until 60+ resolved paper positions at >55% (or maker strategy showing positive net-of-fee capture over 2+ weeks).

## 4. Proposed UUID-Native P&L Pipeline

**Type registry** (resolve the 0x3B0 collision by standardizing on the 0x3A block): `0x3A0` MARKET (Poly or Kalshi; venue in namespace/provenance), `0x3A1` QUOTE, `0x3A2` TRADE (historical/market tape), `0x3A3` ORDER_EVENT (book delta), `0x3A4` KALSHI_BET (our order intent), plus new `0x3A7` FILL, `0x3A8` POSITION_SNAPSHOT, `0x3A9` SETTLEMENT, `0x3AA` PNL_MARK. Provenance: `0x9 KALSHI`, `0x7 POLY_MAKER`, `0x8 TURBO_QUANT` (strategy engine).

**Flow** (all local Postgres, spawn-model per `pipe_a_to_b.py`):

```
tape:    WS quotes  → mint 0x3A1 (signal=mid) ──┐  in-proc bitmask filter (1.5M/s)
signal:  strategy   → edge UUID (0x326-style) ──┼→ risk gate (caps, kill switch)
order:   0x3A4 BET  parent=0x3A0 market ────────┘  client_order_id = low-42 bits
fill:    0x3A7 FILL parent=0x3A4, signal=fill_price, size in payload row
settle:  0x3A9      parent=0x3A0, signal∈{0,1}
mark:    0x3AA      parent=position, signal=unrealized P&L (scaled)
```

**Ledger tables**: `uuid_orders(uuid_hi, uuid_lo, parent_market_hi/lo, side, qty, px, state)`, `uuid_fills(..., parent_order_hi/lo)`, `uuid_positions` (rollup view), `uuid_pnl` — realized P&L is a pure SQL walk of the spawn tree: `SUM(settlement.signal×qty − fill_px×qty − fees)` grouped by `((uuid_hi>>52)&4095)` and market namespace. Because `client_order_id` is derived from the UUID's deterministic 42-bit tail (already implemented in `kalshi_uuid_bot.py`), **every exchange acknowledgment reconciles to a UUID with no lookup table** — the outbox/idempotency pattern from gist `9e78f3ce` becomes a bitmask join. Nightly: re-run `proof_transaction.py` over the ledger; the VERIFICATION.md truth-loop discipline extends naturally — a P&L number is only "PROVEN" when it reconciles against `GetFills` + settlement API output.

**Sequence to first real dollar**: (1) obtain Kalshi API keys, wire into `kalshi_uuid_bot.py`; (2) build fill-poller + ledger tables (~2 days); (3) 2–4 weeks paper via the disposition/consensus gates on the maker + calibration strategies the 19 analyses already validated; (4) go live at $1–5/contract, 5-contract max, daily-loss kill switch; (5) add Polymarket leg (wallet + py-clob-client) for the cross-venue divergence book. Polymarket carries US-access/regulatory ambiguity; Kalshi is the compliant first venue.
